## 三、整体架构（三层解耦，为未来 API 接入预留）

```
第一层 数据获取  src/data/          ← 未来替换为商品系统 API / 物流系统 API
   ├─ product-source.js    接口：list() / search({keyword,limit}) / getBySpu(spu)
   ├─ logistics-source.js  接口：listChannels() / listCountries(ch) / getRules(ch,country)
   └─ local-adapter.js     Demo 阶段的本地实现（读 data/*.data.js）

第二层 业务计算  src/core/          ← 不依赖任何文件格式或 API 返回结构
   ├─ pricing.js    原价 / 默认售价 / 手动售价覆盖
   ├─ costs.js      采购成本 / 重量 / 总成本
   ├─ logistics.js  价目表构建 + 重量段匹配 + 运费计算
   ├─ mix.js        购买占比校验 + 加权汇总
   ├─ money.js      币种换算与金额展示
   ├─ errors.js     异常分类（数据缺失 / 规则不支持 / 输入非法 / 计算失败）
   └─ calculator.js 场景编排：把上述模块串成一次完整测算

第三层 页面展示  src/ui/ + index.html + assets/styles.css
```

**未来接入 API 的改动范围**：仅需新增一个实现同样接口的 Adapter，并替换 `src/data/local-adapter.js` 的装配位置。第二层计算逻辑与第三层页面**不需要修改**。

> 需求 §8 要求「不要为了模拟 API 而编造真实 API 地址、鉴权方式或接口字段」。因此本 Demo **没有**编造任何 API 地址或鉴权字段，仅定义了方法签名与返回结构约定。

## 五、定价规则实现（需求 §5）

配置位置：`config/pricing.config.js` → `pricing`

| 参数 | 默认值 | 含义 |
| --- | --- | --- |
| `baseDiscountRate` | 0.50 | 单件折扣率，用于反推原价 |
| `discountByQty` | `{1:50%, 2:50%, 3:60%, 4:65%}` | 各数量档折扣率 |
| `defaultQtys` | `[1,2,3,4]` | 默认生成的套餐数量 |

计算公式（`src/core/pricing.js`）：

```
单件原价 = 单件售价 ÷ 单件折扣率(50%)
套餐原价 = 单件原价 × 套餐数量
套餐售价 = 套餐原价 × 该数量档折扣率
```

以单件售价 19.99 USD 为例（与需求文档示例一致）：

| 套餐数量 | 套餐原价 | 折扣率 | 默认套餐售价 |
| --- | --- | --- | --- |
| 1 件 | 39.98 | 50% | 19.99 |
| 2 件 | 79.96 | 50% | 39.98 |
| 3 件 | 119.94 | 60% | 71.96 |
| 4 件 | 159.92 | 65% | 103.95 |

### 5.1 手动售价覆盖（需求 §5.3，**必须实现**）

每个套餐有独立的售价输入框与「自动 / 手动」状态：

1. 默认自动：售价随单件售价与折扣率自动计算。
2. 用户改写某个套餐售价 → 该套餐切换为**手动**，标记 `priceMode = 'manual'`，并记录被改动的字段。
3. 再次修改**单件售价**时：仍为「自动」的套餐全部重算；「手动」的套餐**保持原值不变**（不会被覆盖）。
4. 每个套餐提供「恢复自动计算」→ 按**当前**单件售价与折扣率重算该套餐售价。
5. 表格同时展示 **套餐原价 / 折扣率 / 默认计算售价 / 最终套餐售价**，并用「自动 / 手动」标签区分，避免手动值与自动值混淆。
6. 手动改价**只影响售价与依赖售价的派生指标**（套餐客单价、客单系数、费用占比、加权汇总中的客单价），**采购成本、物流成本、总成本不受影响**。

### 5.2 数量与折扣率不写死

套餐数量可在界面增删，默认 1–4 件但**不限于此**：

- 数量必须是**正整数**：0、1.5、负数均报错「套餐数量必须是正整数」，不静默取整。
- 新增的数量档（如 5 件、6 件）在 `discountByQty` 中**没有默认值**时，折扣率留空并提示「请填写折扣率」，**由用户填写而不是工具猜测**（需求 §11.8「对于无法从现有数据或规则中确认的信息，先列出问题，不要自行假设」）。

### 5.3 金额精度

内部全程用浮点原值计算，**只在展示层**做两位小数四舍五入（`src/core/money.js`），避免多次四舍五入累积误差。

## 六、成本计算规则实现（需求 §6）

| 成本项 | 公式 | 实现位置 |
| --- | --- | --- |
| 采购成本 | 单件采购成本 × 套餐数量 | `src/core/costs.js#purchaseCost` |
| 套餐重量 | 单件重量 × 套餐数量（克 → 千克） | `src/core/costs.js#bundleWeight` |
| 物流成本 | 见 §七 | `src/core/logistics.js#calculate` |
| 广告成本 | 每单一个固定值，**所有套餐共用**，不随件数变化 | `src/core/costs.js` |
| 套餐总成本 | 采购 + 物流 + 广告（广告未填写则不计） | `src/core/costs.js#totalCost` |

**广告成本（需求 §6.3）**：

- 输入项为「每笔订单获客成本」，单位与售价币种一致。
- 不填写 → **不计入**总成本，界面显示「未提供」，而不是显示 0。
- 填写 → 所有套餐总成本增加**同一个**金额。
- 输入负数 → 报错。

**币种口径**：成本内部统一以 **CNY** 计价（SPU 采购成本与物流价目表都是人民币）；售价与展示默认 **USD**，汇率 `fx` 可改（默认 1 USD = 6.80 CNY），界面可切换售价币种。

**不做的指标（需求 §7.3）**：本 Demo **不计算**净利润、净利润率、贡献毛利。当前展示的派生指标只有**逐套餐**的「套餐客单价 / 客单系数 / 物流+采购费用 / 物流+采购费用占比」与**订单级**的 6 项加权汇总，避免把「售价 − 已计算成本」误命名成利润。「套餐总成本」只包含当前已纳入的成本项（采购 + 物流 + 广告），**不是完整净成本**。

## 七、物流渠道计价规则实现说明（需求 §6.2）

### 7.1 先读真实规则，再写公式

源文件每行 = 一个「**渠道 × 目的国家/地区 × 重量段**」。规则表里同时给出：

- `piece_price`：**件价**（元/件），作用于订单**件数**；
- `heavy_price`：**计重单价**（元/公斤），作用于订单**总重**；
- `min_weight` / `max_weight`：重量段边界（公斤）。

据此确定计价式：

```
运费(¥) = piece_price × 件数 + heavy_price × 订单总重(kg)
```

实测校验（见 §10 场景5）：该式与独立人工计算样例逐条核对一致。

### 7.2 重量段匹配规则

本轮需求已明确重量段的区间语义为 **左开右闭 `(min, max]`**，即 **min < 订单总重 ≤ max**：

- 重量段按 `min_weight` 升序排列，命中条件为 `weightKg > minWeight && weightKg <= maxWeight`；
- **上界含、下界不含**：落在 0.10 ~ 0.20 kg 的重量段只收 `(0.10, 0.20]`，**200 g 命中 `(0.10, 0.20]`**；
- 命中不到时区分三种原因（提示文案与异常分类一一对应）：
  - 超过最后一段上界 → 「订单总重 X kg **超出该渠道承运上限** Y kg」（规则不支持）；
  - 低于第一段的 `min_weight` → 「订单总重 X kg **低于该渠道的最小计费重量** Y kg」（规则不支持）；
  - 落在两段之间 → 「订单总重 X kg **落在该渠道计价规则的重量空档**（规则数据缺口，需人工确认）」（数据缺失）。

**源数据中真实存在的重量空档（5 处，已在 Demo 中如实提示，不猜测价格）**：

| 渠道 | 目的地 | 空档区间 |
| --- | --- | --- |
| 特惠带电 | 阿联酋 | (2.00, 2.01] kg 与 (5.00, 5.01] kg |
| 特惠普货 | 阿联酋 | (2.00, 2.01] kg 与 (5.00, 5.01] kg |
| 特惠带电 | 萨尔瓦多 | (2.00, 2.01] kg |

> **极通环球专线-标准定制敏感**（13 条，仅美国 / 加拿大）第一段 `min_weight = 0.05 kg`，即**低于 0.05 kg 的订单不落入任何重量段**，页面提示「低于最小计费重量」。

全球承运上限为 **30 kg**。

### 7.3 渠道 × 目的地不支持

所选渠道没有该目的地的任何规则行 → 「渠道「X」不支持目的国家/地区「Y」」。界面在切换渠道时还会检查当前目的地是否仍被支持，若不支持则**自动切到该渠道支持的目的地**并给出显式提示，请用户确认目的地是否正确（不静默改动）。

### 7.4 规则中没有的计费要素 —— 未被擅自补充

需求 §6.2 列举了「首重及续重、最低收费、体积重量、计费重量、附加费用」等可能的参数。**逐条核对源文件后确认：**

| 要素 | 源文件是否提供 | 本 Demo 的处理 |
| --- | --- | --- |
| 件价 | ✅ `piece_price` | 已实现 |
| 计重单价 | ✅ `heavy_price` | 已实现 |
| 重量段 / 承运上限 | ✅ `min_weight` / `max_weight` | 已实现 |
| 首重 / 续重 | ❌ 无独立字段 | 未实现（件价 + 计重单价已构成完整计价式） |
| 最低收费 | ❌ 无 | 未实现，**不自行设定起收金额** |
| 体积重量 / 计费重量 | ❌ 无 | 未实现；当前按**实际重量**计费 |
| 附加费用（偏远、燃油等） | ❌ 无 | 未实现 |
| `gofo_usd_price` | 有列但 **446 行全为空** | 不参与计算（见 §11） |

> 说明：计价式是**从真实规则字段读出来的**，不是"按经验套一个线性公式"；同时也没有为了凑齐需求列举的参数而虚构收费规则。

### 7.5 计算可追溯

每个套餐的物流成本都可展开一行**计价明细**，显示：命中的渠道与目的地、命中重量段 `(min, max]` kg、件价与件数、计重单价与实际重量、生效日期，以及类似

> 云途全球专线挂号（特惠带电）· 美国 · 重量段 (0.30, 0.45] kg → 件价 ¥31.85 × 1 件 + 计重 ¥72.69/kg × 0.350 kg = ¥57.29

的完整算式，满足需求 §6.2「计算结果应能追溯使用了哪个物流渠道、哪些参数和哪条计价规则」。

### 7.6 与未来物流 API 解耦

`src/core/logistics.js` 只接收「规则行数组」，不认识数据来源。`src/data/logistics-source.js` 把适配器返回的规则行**归一化**为统一结构（`business/channel/country/minWeight/maxWeight/heavyPrice/piecePrice/effectiveDate`）后再交给计算引擎。因此未来接入物流系统 API 时，只要新 Adapter 返回同样结构的规则行，计价引擎与页面均无需改动。

## 八、订单结构汇总与派生指标（需求 §7.2 / §7.3）

### 8.1 逐套餐派生指标（结果表内，本轮新增）

以下指标为**纯展示层派生**（实现于 `src/ui/render.js#derivedMetrics`），**不参与计算内核**，不改变任何成本口径：

| 指标 | 计算方式 | 展示位置 |
| --- | --- | --- |
| 套餐客单价 | 套餐最终售价（自动计算或人工调整后的最终价格） | 结果表「定价表现」组 |
| 客单系数 | 套餐客单价 ÷ 单件售价 | 结果表「定价表现」组 |
| 物流+采购费用 | 采购成本 + 物流成本 | 结果表「商品及物流成本」组 |
| 物流+采购费用占比 | (采购成本 + 物流成本) ÷ 套餐客单价，**不含广告成本** | 结果表「商品及物流成本」组 |

任一前置值不可算（如单件售价为空、成本项缺失）时，对应单元格显示**具体原因**（如「未计算 · 重量缺失」），**不默认填 0**。

### 8.2 订单结构加权汇总（结果区指标卡）

「套餐购买占比」为**可选**输入，填在「测算输入」区的 D 组里：

| 指标 | 计算方式 |
| --- | --- |
| 预计客单价 | Σ(套餐最终售价 × 占比) |
| 平均每单采购成本 | Σ(套餐采购成本 × 占比) |
| 平均每单物流成本 | Σ(套餐物流成本 × 占比) |
| 平均每单广告成本 | 各套餐共用的订单广告成本（未填写时显示「未提供」） |
| 平均每单总成本 | Σ(套餐总成本 × 占比) |
| 平均每单购买数量 | Σ(套餐数量 × 占比) |

校验口径：

- 全部不填 → **不展示**加权汇总，只展示各套餐单独测算结果；
- 合计 ≠ 100% → 明确报错并显示当前实际合计；
- 只填部分 → 提示「已填写部分购买占比，请补齐其余套餐（缺少 N 件档）」，同时显示当前合计（不隐藏用户已填内容）；
- 存在未计算成本项 → **不做**加权汇总（避免用缺失值当 0 求和）。

| # | 场景 | 提示 |

| 3 | 重量/尺寸缺失 | 重量缺失 → 运费「未计算」并说明原因；尺寸缺失 → 提示源数据无尺寸信息 |

| 5 | 物流规则缺少必要参数 | 价目表未装载 / 规则缺参数时明确提示 |
| 6 | 物流费用计算失败 | 计算失败分类提示，总成本随之不可计算 |
| 7 | 套餐数量不合法 | 正整数校验 |

| 9 | 折扣率不合法 | 「折扣率必须在 0% ~ 100% 之间」 |

## 十一、已知限制

1. **`gofo_usd_price` 全列为空**：446 行全部无值，无法用于计算，本 Demo 忽略该列。若该字段后续有含义（推测为 GOFO 渠道美元价），需要业务补充规则后再实现。
2. **重量空档**：阿联酋、萨尔瓦多有 **5 处**重量区间缺规则（见 §7.2）。Demo 如实提示"需人工确认"，**不插值、不外推**价格。
3. **无体积重量 / 首重 / 最低收费 / 附加费用**：源规则中没有这些字段，当前按实际重量线性计费。若真实计费含这些项，需先补数据。
4. **SPU 无币种列、无尺寸列**：采购成本按 ¥ 解读（源文件未标币种）；尺寸（长/宽/高）已按需求移除，当前物流规则也不按体积计费，故不影响运费。**带电属性已由本版 `elec` 列提供**，映射逻辑已实现并有测试覆盖；但当前数据集 `elec` 全为 `0`，缺带电商品的真实样本（见 §4.1 与 §十二 第 5 条）。
5. **「是否敏感」「是否尺寸超限」无台账数据**：这两个字段是本轮新增的**用户手填选填项**，SPU 台账中没有，也无从统计真实占比 —— 全部商品默认「否」，需人工补充。这会直接影响默认渠道在「尺寸超限」「敏感」两级上的分流结果（见 §4.1）。

8. **不含支付手续费 / 税费 / 退款 / 平台费用**：因此不提供净利润与利润率指标（需求 §7.3 明确本期不做）。
9. **数据加载在浏览器端**：1369 条 SPU + 446 条规则全部内嵌为 JS（合计约 284 KB），适合 Demo；生产环境应改为接口按需查询。

## 十二、需要业务确认的问题

> 需求 §11.8：「对于无法从现有数据或规则中确认的信息，先列出问题，不要自行假设。」以下 6 条均**未**在代码中擅自定案。

1. **件价 + 计重单价的计费口径是否完整？**

2. **重量空档是否需要补数据**
   重量段的边界语义本轮需求已明确为 **左开右闭 `(min, max]`**（200 g 命中 `(0.1, 0.2]`），Demo 已按此实现，不再是待确认项。**仍需确认**：阿联酋 / 萨尔瓦多的 **5 处 0.01 kg 空档**是**数据遗漏**还是**业务上确实不接**？若是遗漏，需补数据；若是业务限制，则当前提示口径正确。

3. **SPU 采购成本的币种**
   源文件无币种列，本 Demo 按 ¥ 解读。若实际为美元或其他币种，请指定，我方改配置即可（不影响计算结构）。

4. **汇率取值与更新方式**

## 十六、本轮变更说明（集中输入 + 集中输出）

本轮需求方明确要求：**保留现有业务计算逻辑、SPU 数据、物流计价规则与功能，不推翻重做**，只优化**页面信息架构、输入交互与结果展示**。核心方向是让页面形成清晰的操作习惯 —— **先集中填写测算条件，再集中查看各套餐的定价表现和成本结果**。

### 16.1 页面结构：5 个独立大卡片 → 2 个主区域

| 改前 | 改后 |
| --- | --- |
| 商品信息（卡片 1）／套餐配置与定价（卡片 2）／成本配置（卡片 3）／结果（卡片 4）／订单结构汇总（卡片 5） | **① 测算输入**（`#sec-input`，单个面板内含 4 个分组）+ **② 测算结果**（`#sec-output`，结果表 + 汇总卡） |

输入区内的 4 个分组：

| 分组 | 内容 |
| --- | --- |
| **A 商品信息** | 数据来源切换（按 SPU 选择 / 手动录入）、SPU 检索与选择、商品名称、单件采购成本、采购成本币种、单件重量、是否带电、是否敏感※、是否尺寸超限※（※ 为用户补充选填项） |
| **B 套餐定价** | 单件售价、单件折扣率（默认 50%）、默认折扣率说明、套餐数量 / 折扣率 / 售价 / 默认售价 / 计算方式 / 操作 的套餐表、新增套餐按钮 |
| **C 物流与其他成本** | 物流渠道、目的国家/地区、每笔订单广告成本（可选）、渠道规则信息、查看重量段计价规则 |
| **D 订单结构（购买占比）** | 各套餐购买占比输入、合计校验与提示（原「订单结构汇总」卡片里的**输入部分**整体迁入此处） |

### 16.2 结果表：新增 4 个逐套餐关键指标

结果表由 11 列构成，表头按**两行分组**呈现：

| 分组 | 列 |
| --- | --- |
| 定价表现 | 套餐原价、折扣率、**套餐客单价**、**客单系数** |
| 商品及物流成本 | 采购成本、物流成本、**物流+采购费用**、**物流+采购费用占比** |
| 其他成本 | 广告成本、套餐总成本 |

- **套餐客单价** = 最终实际售价（自动计算或人工调整后的最终价格）。
- **客单系数** = 套餐客单价 ÷ 单件售价。
- **物流+采购费用** = 采购成本 + 物流成本。
- **物流+采购费用占比** = (采购成本 + 物流成本) ÷ 套餐客单价，**不含广告成本**。
- 「套餐总成本」= 采购 + 物流 + 广告，**只含当前已纳入的成本项，不等于完整净成本**。
- 成本算不出来时显示**具体原因**（如「重量缺失」「渠道不支持该目的地」），不默认填 0。
- 主表移除「默认售价」（输入区套餐表已有）与「套餐重量」（展开的运费明细里已有），避免横向滚动。
- 各表头带 `title` 计算口径悬浮提示。

### 16.3 汇总指标卡精简为 6 张

预计客单价、平均每单采购成本、平均每单物流成本、平均每单广告成本、平均每单总成本、平均每单购买数量。**未填写购买占比时不展示加权汇总**，仅显示引导性空态提示。

### 16.4 其它交互与视觉调整

- 商品信息区分**系统获取**与**用户补充**：SPU 模式下台账字段只读（灰底 + 「来源：SPU 台账（只读）」徽章），「是否敏感」「是否尺寸超限」标注「用户补充 · 选填」并单独高亮。

- 字段命名统一为「套餐客单价 / 客单系数 / 物流+采购费用 / 物流+采购费用占比 / 套餐总成本」。
- 购买占比输入框沿用**标准左→右累积**逻辑（输入 `4` 得 `40`），且**不重建 DOM**（避免重渲染导致光标跳位与数字倒序的老问题）。
- 购买占比为**可选**：未填写时不影响任何套餐的单独测算。
